# SEC-OPS V8 — Snapshot Evidence & Event Traceability Report

## 1. End-to-End Snapshot Pipeline Architecture (Phases 7 & 8)

The SEC-OPS V8 visual evidence system operates end-to-end with persistent disk storage, database indexing, and annotated overlays:

```text
REAL RTSP CAMERA FEED
          ↓
OpenCV Frame Acquisition
          ↓
YOLOX Deep Learning Inference (Bounding Boxes, Confidences, Classes)
          ↓
ByteTrack Trajectory Correlation (Track IDs)
          ↓
OpenCV Overlay Renderer (Dynamic Boxes, Classes, Scores, Timestamps, Camera IDs)
          ↓
Persistent Storage (JPEG / Object Storage under /snapshots/)
          ↓
Database Entity Linkage (EvidenceArtifact / ExitEvent.snapshot_url)
          ↓
REST API (FastAPI Static File Mount / api/cameras/{id}/snapshot)
          ↓
Frontend Dashboard Viewer (StreamPlayer Modal / Event Evidence Modal)
```

### Black Screen & Blank Screen Remediation
* **Root Cause Fixed**: Previously, if a snapshot image failed to load or the camera had not yet written a frame, the container defaulted to pure black (`bg-black`) without an error state.
* **Production Fix**:
  * Frontend components (`StreamPlayer`, `EventsPage`, `DashboardPage`) now listen to image `onError` events.
  * When an image is missing or unreachable, the UI transitions to a clear, professional **"Snapshot Unavailable"** card stating:
    > *"No visual evidence frame was recorded for this camera or the stream was in standby."*
  * No black screens or broken browser icons are rendered.

## 2. Dynamic Snapshot Annotation (Phase 8)

All snapshot images generated by the visual inspection engine include burnt-in forensic annotations:
1. **Bounding Box**: Crisp rectangles enclosing detected subjects and merchandise.
2. **Label**: Verified class name (e.g. `PERSON`, `BOTTLE`, `CARTON`).
3. **Confidence**: Model certainty percentage (e.g. `94.2%`).
4. **Track ID**: Unique ByteTrack persistent identifier (e.g. `TRK-104`).
5. **No Static/Fake Boxes**: Bounding boxes are drawn exclusively from actual YOLOX detection coordinates.

## 3. Globally Unique Event Identifiers & React Key Safety (Phase 31)

### The Duplicate Key Bug Resolution
* **Previous Error**:
  ```text
  Warning: Encountered two children with the same key, `MOV-EVT-2026`
  ```
* **Root Cause**: The backend events endpoint previously formatted IDs as `f"MOV-{ev.event_id[:8]}"`. Because timestamps began with `EVT-2026-...`, string truncation collapsed distinct events into the identical string `MOV-EVT-2026`.
* **Resolution**:
  * Event ID formatting now retains the full UUID: `f"MOV-{ev.event_id}"` and `f"INV-{ev.event_id}"`.
  * Event generation in ingest pipelines uses cryptographically random UUIDs:
    ```python
    event_id = f"EVT-{int(now.timestamp())}-{uuid.uuid4().hex[:6].upper()}"
    ```
  * Database schema strictly enforces `UNIQUE(event_id)`.
  * All frontend table rows use the persistent unique database identifier as their React `key`.
